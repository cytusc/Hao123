## 1. 度量观测：先验证 P0 收益

### 1.1 北极星与采样边界

原战略北极星包含「当周活跃、完成云端配置、次周回访」。次周回访需要成熟的周队列，不能用一次实时查询直接证明。本期先提供代理指标 **WAU-Personalized-Observed（可观测周活跃个性化用户数）**：

- 统计时点前 7×24 小时内有已记录的公共站点点击。
- 当前云端 `preferences.custom` 或 `preferences.pinned` 非空。
- 当前为启用的普通用户，且个性化开关开启；按用户去重。

活跃证据复用 `user_site_stats.last_clicked`。该表保存网站级聚合，能够判断是否最近点击，但无法还原历史每周访问或历史配置状态。用户关闭个性化、清空记录或删除相关标签后可能退出统计；私人自定义网址点击不进入该表，游客也不进入统计。报表必须展示上述边界，不能把该代理指标标成全站真实 WAU，也不能以此推导留存下降。

配套提供「可观测周活跃用户数」和「当前有云端个性化配置的用户数」，区分活跃与配置存量。后续若需要严格次周留存，另行评审周级去重队列、配置快照与隐私告知；仅保存每周总人数不足以计算两个星期的用户交集。本期不引入逐条点击事件。

### 1.2 过程指标与正确解释

窗口默认近 7×24 小时；累计用户口径排除管理员、停用账号。所有分母为零的比率返回空值并附样本数，避免把「无样本」展示为 0%。

| 指标 | 定义 | 解释与门禁 |
| --- | --- | --- |
| 配置冲突率 | `prefs_conflict / (prefs_save + prefs_conflict)` | 分母为校验通过后的保存尝试；400、鉴权失败及数据库异常另计故障。成功 400 次、冲突 12 次时约为 2.91% |
| 找回事件比 | `reset_success / forgot_request_eligible` | 分母为限流通过且匹配启用普通账号的找回请求；重复请求和跨窗口重置使其不等于严格转化率，可能超过 100% |
| 成熟找回完成率 | 发信成功的去重找回流程中，令牌有效期内重置成功的流程占比 | 按流程归因，等待 1 小时有效期结束后进入分母；SMTP 接受不等于邮件最终进箱。首期若不做归因，只展示事件比，不设置 60% 硬门禁 |
| 邮箱验证率 | 启用普通账号中的已验证人数 / 启用普通账号人数 | 账号存量指标；重置密码也会置已验证，不能全部归因为验证链接点击 |
| 注册与登录量 | 成功 `register` / `login` 事件数 | 登录次数不是活跃人数；管理员操作单独排除 |
| 同步故障与埋点漏记 | 业务写入异常数、埋点失败数及接口故障情况 | 防止事件漏写制造虚假的低冲突率；与业务指标一起查看 |

版本锁上线后 409 可能增加，因为原来被静默覆盖的写入现在被识别。冲突率接近零既可能代表少冲突，也可能代表使用量低或漏记。P0 的首要验收是「过期版本不能覆盖、冲突后可完成处理」，后续再看冲突发生率、解决率和同步故障。

找回流程归因建议使用独立随机 `flow_id`，只关联找回与重置结果；它不能是邮箱、邮件令牌或令牌摘要。成功邮件对应的令牌记录需关联该流程。发信失败、限流、未知邮箱保持用户响应一致，指标仅供管理员聚合查看。若引入该归因，应单列工作量与数据库变更。

### 1.3 事件底座与埋点方案

拟新增 `events` 表，包含独立事件 ID、`kind`、白名单 `payload`、`created_at`、可空 `user_id`。`kind` 约束为 `register/login/verify_email/forgot_request/reset_success/prefs_save/prefs_conflict/tag_delete/tag_clear`；配套时间、种类与归因查询所需索引。用户关联采用可删除设计，用户删除后清理相关事件。

拟新增 `recordEvent`，采用有超时上限的 best-effort 写入，失败只记录不含个人信息的错误类型和失败计数，不影响业务响应。成功事件在业务事务提交后记录；冲突事件在确认 409 后记录。该方式存在提交后进程退出导致漏记的窗口，因此本期指标用于趋势观察；如需审计级完整性，再评审事务发件箱。

| 事件 | 真实插桩位置 | 计数条件 |
| --- | --- | --- |
| `register` / `login` | `backend/auth.go` 的同名处理函数 | 普通用户会话事务提交成功；注册邮件失败仍计注册成功 |
| `forgot_request` | `backend/email_auth.go` 的 `forgotPassword` | 请求解码且限流通过；payload 仅记录匹配与发信结果枚举，报表以 eligible 子集为分母 |
| `verify_email` / `reset_success` | `verifyEmail` / `resetPassword`，关联 `consumeEmailToken` | 令牌事务成功提交；需要成功用户 ID 的内部结果传递 |
| `prefs_save` / `prefs_conflict` | `backend/recommend.go` 的 `savePrefs` | 条件更新成功 / 版本过期；重试也计一次尝试 |
| `tag_delete` / `tag_clear` | `deleteProfileTag` / `clearHistory` | 幂等请求成功，仅表示操作次数；不等于实际删除标签数 |

payload 限定为结果枚举、计数与必要的独立流程标识，不记录邮箱、IP、UA、令牌、网址、站点 ID、偏好全文或标签内容。操作观测与行为画像分开说明；关闭个性化后，点击门禁仍保持不记录。隐私说明应解释账户安全与同步操作的最小观测用途。

保留期限为 90 天，需有每日清理任务与失败告警；仅在重启时清理无法保证期限。长期趋势只保存不含用户 ID 的日/周汇总。清空或删除标签对画像与实时活跃计数的影响须在报表说明；账户观测事件不含被删除的兴趣内容。

新增表可复用 `schema.sql` 与 `initialize` 的幂等初始化事务，但这仍是数据库迁移，需要评估锁等待和回滚；不能承诺「零迁移风险」。回滚应用时优先保留新增表，避免丢失数据。

### 1.5 验收与观察

- Given 无数据，When 管理员读取指标，Then 计数为零、比率为空，时间窗与采样边界清晰；游客或普通用户无法读取。
- Given 两设备以同版本保存，When 一个成功、另一个 409，Then 各新增一个对应事件，冲突率为 50%，云端配置未被过期写入覆盖。
- Given 埋点写入失败，When 注册、重置或保存已成功，Then 业务仍成功且产生漏记告警，不记录任何凭据。
- Given 个性化关闭或标签清空，When 读取活跃指标，Then 不新增点击事件，报表说明可观测样本变化。
- Given 成功、失败及重复的找回请求，When 聚合，Then eligible、SMTP 接受与重置成功可区分，找回事件比不冒充转化率。
- Given 数据超过 90 天，When 每日清理任务执行，Then 明细删除且汇总保留；失败可发现。

采集上线后观察 1–2 周，建立样本与故障基线；此前 P0 未埋点，不能补造上线前的冲突率。进入增长实验的门禁为同步无静默覆盖、找回链路可用、漏记可监控；具体率值和最小样本数在基线建立后评审。

工作量：M；流程归因、定时清理及管理展示纳入估算。依赖：真实 SMTP 配置、任务调度方式、指标与隐私口径确认。

## 3. P1-2 推荐运营调参

优先级：P1 ｜ 工作量：M（含灰度与回归）｜ 类型：后端配置与后台表单

现状：`recommend.go` 的 `click`、`decayed`、热门与相似访问查询使用 7 天衰减；`rankSites` 的默认权重为精选 0.15、热门 0.3、个人 4、相似 2、分类 0.4。后台 `Admin.jsx` 已有 `recommendation` 页，适合增加配置表单。`app_meta.value` 当前为 text，需要解析与校验。

### 3.1 首期配置与推荐基线

| 配置项 | 默认值 | 建议范围 | 首期作用域 |
| --- | --- | --- | --- |
| `reco_half_life_days` | 7 | 1–30 天 | 个性化读取时的尾部衰减 |
| `reco_w_base` | 0.15 | 0–1 | 个性化排序的精选项 |
| `reco_w_popular` | 0.3 | 0–2 | 个性化排序的热门项 |
| `reco_w_personal` | 4 | 0–10 | 个人常用项 |
| `reco_w_co` | 2 | 0–5 | 相似访问项 |
| `reco_w_category` | 0.4 | 0–2 | 分类项 |

范围为评审建议；配置必须是有限数值，不能全部权重为零。一次请求使用同一个已验证配置快照。缺失或损坏配置回退默认值并告警，不能让推荐接口失败。

为兑现「关闭个性化与游客基线不受影响」，首期将精选/匿名热门的衰减与权重固定为现有默认值；以上配置仅作用于开启个性化的推荐分支。不能同时把全局热门衰减改掉，又承诺关闭个性化后的排序不变。

### 3.2 历史聚合的限制

`user_site_stats.score` 已按 7 天折叠历史点击。修改半衰期无法精确重建历史行为；只有累计点击、最后时间与衰减分数，没有逐条历史可重放。

首期保留 `click` 的 7 天聚合写入及匿名热门默认查询，只对个人与相似信号从现存分数到当前时点的尾部衰减调参。后台明确标注「历史累计仍按原规则，参数控制当前读取衰减」，14 天方案只能验收这个有限作用域。

若产品需要所有新旧行为都按新半衰期精确计分，应另开评分版本与聚合迁移方案，评估新版本计分起点及灰度隔离；不为重算历史引入逐条访问日志。此项不隐藏在配置表单工作量中。

### 3.3 接口、灰度与验收

拟新增 `GET/PUT /api/admin/reco-config`：返回默认值、当前生效值、配置版本、作用域及更新时间；PUT 校验整个配置并原子保存，携带版本防止管理员相互覆盖。修改记录保留操作人、前后值与配置版本，区别于 90 天产品事件；保留期限另行确认。

后台提供预览、恢复默认及明确发布操作。灰度使用稳定用户分组，返回生效配置版本；首期所有实验共享原有聚合输入，灰度仅改变读取与排序。支持回滚上一版。观察指标结合推荐曝光/点击实验另行评审，WAU 单独不足以验证排序质量。

落点：[recommend.go](../../backend/recommend.go) 的 `decayed`、`rankSites`、`recommendations`；[main.go](../../backend/main.go) 的 `mux`；[schema.sql](../../backend/schema.sql) 的 `app_meta` 及拟议配置审计结构；[Admin.jsx](../../src/Admin.jsx) 的推荐页；[admin.css](../../src/admin.css)；[API.md](../../backend/API.md)。配置加载与管理处理函数为拟新增，参考 [admin.go](../../backend/admin.go) 的 `overview` 和现有 admin 路由规范。

验收：相同聚合输入与统计时点下，14 天参数使个人/相似信号尾部衰减慢于 7 天；构造排序样本可证明各权重有效；游客和关闭个性化用户排序与默认基线一致。非法值、陈旧版本、非管理员写入被拒绝；默认配置保持现有排序、理由、置顶及隐藏规则。灰度用户稳定归组且可回滚。

## 4. P1-3 微信网站 OAuth 与身份绑定

优先级：P1 ｜ 工作量：L ｜ 类型：身份模型与登录流程

Web 首期选微信开放平台「网站应用扫码登录」。使用 `qrconnect` 发起授权，回调后通过网页 OAuth 的 `sns/oauth2/access_token` 换取凭据，再按授权范围获取身份。`code2session` 属于小程序登录，不能用于该网站扫码流程。公众号内网页授权是另一接入场景；手机浏览器是否支持合适的授权体验需单独验证，不承诺扫码流程覆盖所有移动端。

### 4.1 身份与账户模型

建议采用独立 `user_identities`，按 provider、应用标识及 provider_subject 建唯一约束，关联单一 user。微信 OpenID 按 AppID 隔离；只有在同一开放平台且实际取得可信 UnionID 时，才可按其规则处理跨应用身份。

OAuth 账号允许没有邮箱和密码，因此 `users.email`、`password_hash` 需允许空值；保留非空规范化邮箱唯一约束。避免伪造邮箱或占位密码。邮箱注册、改密、找回、用户列表与邮箱状态展示均需适配；OAuth-only 用户不能通过邮箱找回，绑定邮箱前需独立验证。

微信通常不提供邮箱，不能按所谓「同邮箱」自动合并。已有用户须先以现有账号登录并近期重新认证，再授权绑定微信；未经双方身份控制权验证不能合并两个既有账号。首期支持「绑定到当前账号」，跨账号数据合并独立排期。解绑应确保剩余至少一种可用登录方式。

### 4.2 流程、落点与验收

拟新增 OAuth start / callback 与绑定入口；`state` 为短时、一次性随机值并绑定当前浏览器与操作目的，禁止任意回跳地址。并发回调通过身份唯一约束确保只建一个账号；失败事务不能留下半绑定状态。Secret、code 和 access_token 不进入响应或日志，不作为长期会话保存。

会话签发复用 `auth.go` 的 `issueSession`，在账户/身份事务内写会话并在提交后设置 Cookie，保持用户行锁、停用检查与重置撤销语义；不复用已不存在的 `createSession`。

落点：[schema.sql](../../backend/schema.sql)、[auth.go](../../backend/auth.go)、[main.go](../../backend/main.go) 的 `mux`、[AuthDialog.jsx](../../src/AuthDialog.jsx) 的登录按钮、[AccountDialogs.jsx](../../src/AccountDialogs.jsx) 的绑定入口、[API.md](../../backend/API.md)、[.env.example](../../backend/.env.example)。`backend/oauth.go` 为拟新增模块。

验收：首次授权建普通用户、后续登录同一 user；重复或并发回调不重复建号；无效、过期或复用 state 被拒绝。已登录邮箱用户绑定后两入口到同一 user；已绑定他人的身份不能被夺取。无邮箱用户不会进入邮箱验证/改密死路；停用账号不能通过 OAuth 绕过限制。提供授权拒绝、网络异常与资质未就绪的可理解反馈。

依赖：微信开放平台网站应用 AppID、Secret、审核和回调域名配置；具体备案要求按平台资质流程核实。公众号、小程序、Apple / Google 与跨账号数据合并不在首期范围。

## 5. P1-4 轻量 AI 入口补强

优先级：P1 ｜ 工作量：S/M ｜ 类型：目录数据与展示补强

现状：`backend/seed.json` 与 `src/data.js` 已有 `ai` 分类和 10 个 AI 站点；`src/main.jsx` 已有 AI 分类按钮和「试试 AI 新工具」区块，展示固定 ID 的三个站点。已有数据库在 `app_meta` 标记 `seed-v1` 后不会因修改 seed 自动重灌，因此改种子不能视为已有库的内容更新方案。

方案：

1. 内容运营核验现有清单，维持 8–15 个精选站点，每项补充用途、官网地址、访问限制与核验日期。清单齐备后通过现有后台目录管理或投稿审核更新已有数据库。
2. 首页 AI 快捷区从 `/catalog` 的 `ai` 分类选取已批准、未被用户隐藏的站点，并按目录排序展示少量项目，避免固定 ID 对下架或换站失效。空分类或全部隐藏时优雅收起。
3. 复用现有 `link` / `record`、置顶和隐藏流程；无效或下架站点不可展示，普通点击遵守个性化关闭门禁。保持轻量直达，不引入对话 API、模型调用及批量大全。
4. 种子清单仅服务新库，已有库内容更新需有可复核清单；保留运营调整，不由启动过程反复覆盖。

落点：[main.jsx](../../src/main.jsx) 的 `ai-discovery`、`link`、`chooseCategory`；[styles.css](../../src/styles.css)；[catalog.go](../../backend/catalog.go) 的 `catalog` / `createSite` / `updateSite`；[admin.go](../../backend/admin.go) 的 `review`；[seed.json](../../backend/seed.json)、[data.js](../../src/data.js) 的初始/备用目录。`navigation.jsx` 仅在需要目录数据派生时涉及，不作为 AI 区块的渲染位置。

验收：目录增删、排序或下架后，刷新即可正确更新快捷区；不依赖种子 ID。站点可直达、置顶、隐藏；隐藏后不出现在快捷区。关闭个性化时不记录点击；窄屏入口可达，空清单不报错。已有库不因重启覆盖人工运营内容。

依赖：运营确认精选标准与清单。新增「AI 提问」轻入口仍需单独产品评审，本项不等同于已完成 Q3 的全部 AI 入口目标。
